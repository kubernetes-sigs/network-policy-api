# Network Policy API Conformance Reports

This directory is the official record of which implementations conform to the
Network Policy API. A conformance report is generated by the conformance test
suite itself and records, for each conformance profile, the standard and
experimental test results along with exactly which experimental features the
implementation declared support for — together with a link to the CI job that
produced it.

Reports exist so that support claims are verifiable: instead of a
self-maintained feature list, users get machine-generated results with CI
provenance. Implementations listed on the
[implementations page](https://network-policy-api.sigs.k8s.io/implementations/)
are strongly encouraged to substantiate their entries with a report here.

The reporting process is defined by
[NPEP-137](https://network-policy-api.sigs.k8s.io/npeps/npep-137-conformance-profiles/).

## Directory structure

One directory per Network Policy API release, one report file per
implementation, named after the project:

```text
conformance/reports
|-- v0.2.0
|   |-- kube-network-policies.yaml
|   |-- acme-cni.yaml
|-- v0.1.2
|   |-- ovn-kubernetes.yaml
```

> **Note:** `v0.1.2/ovn-kubernetes.yaml` is a historical report predating the
> v1alpha2 `ClusterNetworkPolicy` consolidation (NPEP-285): it reports the
> v1alpha1-era `AdminNetworkPolicy`/`BaselineAdminNetworkPolicy` profiles in
> an older report layout. It is kept for the record and is not a template for
> new submissions.

## Generating a report

Prerequisites and general suite usage are documented on the
[conformance page](https://network-policy-api.sigs.k8s.io/conformance/). In
short, you need a multi-node cluster running your implementation, with the
`ClusterNetworkPolicy` CRD installed from the release channel you are
certifying.

Run the suite from the Network Policy API release you are certifying against
(check out the corresponding tag, e.g. `v0.2.0`), passing your
implementation's details:

```shell
go test -v ./conformance -run TestConformanceProfiles -timeout 20m -args \
    --conformance-profiles=ClusterNetworkPolicy \
    --organization=<your organization> \
    --project=<your project> \
    --url=<project url> \
    --version=<implementation version being certified> \
    --contact=<comma-separated maintainer contacts> \
    --additional-info=<link to the public CI run that generated this report> \
    --all-features \
    --report-output=<project>.yaml
```

If the implementation does not support every experimental feature, replace
`--all-features` with an explicit `--supported-features` selection; features
that are not enabled are recorded in the report as `unsupportedFeatures`, and
their tests are skipped without affecting the standard result.

This project's own CI performs exactly such a run for kube-network-policies
on every pull request — see
[`.github/workflows/conformance.yml`](../../.github/workflows/conformance.yml)
for a complete working example.

## What a report contains

Abridged example (values are illustrative):

```yaml
apiVersion: policy.networking.k8s.io/v1alpha1
date: "2026-08-02T10:00:00Z"
implementation:
  additionalInformation: https://github.com/my-org/my-project/actions/runs/123456789
  contact:
  - '@my-org/maintainers'
  organization: my-org
  project: my-project
  url: https://github.com/my-org/my-project
  version: v1.2.3
kind: ConformanceReport
networkPolicyV2APIVersion: v0.2.0
profiles:
- experimental:
    result: success
    statistics:
      Failed: 0
      Passed: 4
      Skipped: 0
    summary: ""
    supportedFeatures:
    - ClusterNetworkPolicyEgressNodePeers
    - ClusterNetworkPolicyNamedPorts
  name: ClusterNetworkPolicy
  standard:
    result: success
    statistics:
      Failed: 0
      Passed: 19
      Skipped: 0
    summary: ""
```

The `result` field summarizes each support level:

- `success` — every test at that level ran and passed (for the experimental
  level: every test for the features the implementation declared support
  for).
- `partial` — no failures, but some tests were skipped. Skipped standard
  tests mean the implementation cannot be considered conformant.
- `failure` — one or more tests failed.

## Submitting a report

Open a pull request against this repository that adds your report as

```text
conformance/reports/<Network Policy API release>/<project>.yaml
```

and make sure that:

- [ ] the report was generated by an unmodified conformance suite at the
      release being certified, and is submitted exactly as generated;
- [ ] `implementation.version` identifies a specific snapshot of your project
      (a release, tag, or commit — not a branch name);
- [ ] `additionalInformation` links to a public CI run or job definition that
      shows how the report was produced — maintainers use it to verify the
      report's provenance before accepting it;
- [ ] the standard `result` is `success`;
- [ ] your entry on the
      [implementations page](https://network-policy-api.sigs.k8s.io/implementations/)
      links to the submitted report (or is added in the same pull request).

Maintainers review the pull request and, by merging it, formally recognize
the implementation's conformance.
